# Compose features early, spend review deliberately

Daisy’s workflow demonstrably spends effort waiting on publication, repeating proof, and reconciling task state before delivering a composed feature. Independent review also catches important defects that passing CI misses. **Keep that review, but separate its conclusion from CI, compose a working user journey earlier, and review fixes as deltas.** The evidence does not establish that Daisy is universally slower than PageSpace: recent raw PR medians favor Daisy, while its upper tail is longer. This audit inventories **292 accessible conversation files, 219 Daisy PRs and 2,448 PageSpace PRs**; semantic conversation and diff audits target important cases rather than every transcript line or code change. Conversation availability is heavily asymmetric, lifecycle timings include idle and merge wait, and no defensible overall speed multiplier or billed-cost comparison follows. ([Conversation coverage](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/conversations.md>), [PR audit](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/prs.md>))

## Daisy’s longer tail matters more than its median

Among PRs created October 1–8, merged Daisy PRs have a **55.65-minute median** creation-to-merge duration versus **82.13 minutes for PageSpace**. At the 75th percentile, Daisy takes **6.44 hours versus 2.51 hours**. Daisy has 41 PRs in that cohort, of which 34 merged; PageSpace has 106, all merged. Excluding Daisy’s seven closed unmerged PRs creates selection bias, and the cohorts are unmatched in scope, risk and integration topology. These are observed wall-clock durations, not active agent time or time to the first working feature. They support investigating expensive Daisy outliers, not declaring a universal slowdown. ([Timestamp calculations](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/remote-pr-metrics.json>))

PR counts obscure composition. Local first-parent history recognizes 31 Daisy mainline PR merges versus five PageSpace merges during October 1–8, but PageSpace’s [Imago integration #2852](https://github.com/2witstudios/pagespace/pull/2852) folds many nested feature PRs into one merge: 706 changed paths and 122,420 inserted/deleted text lines. Daisy’s [Round cutover #211](https://github.com/2witstudios/daisydebate/pull/211) changes 293 paths and 67,249 text lines. Counting merged boxes would misrepresent both output and effort. The relevant outcome is how early the complete journey works, then how much work is needed to make it safe to ship. ([Local change inventory](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/local-pr-metrics.json>))

## Preserve behavioral catches and remove duplicated proof

Review is doing real work. The inspected #205 hydration fix initializes state from actual form controls so input entered before hydration survives. #211 fixes stale segment commands, unrelated scratch-document exposure, and asynchronous playback/ballot finalization. PageSpace’s [#2855](https://github.com/2witstudios/pagespace/pull/2855) also fixes capability advertising for scoped MCP tools. These are correctness, privacy and boundary invariants; a blanket green build does not establish them. ([Diff audit and commits](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/prs.md>))

The existing **`review-record` primitive already identifies the exact head, builder and independent reviewer**. Its GitHub workflow does not depend on CI’s job graph. Coupling instead lives in the prompt and verifier: clean approval with zero minors/nits requires integration PASS text and a negative-control declaration, while approval with a minor avoids that extra condition. Evidence requirements should depend on risk and coverage, never on finding count. Keep exact SHA, distinct reviewer identity, severity enforcement and fail-closed records; publish the review conclusion independently, and let required CI establish merge readiness separately. ([Primitive audit](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/workflow.md>), [Verifier](</Users/jono/dev/daisydebate/scripts/review-record.ts:139>))

Give one independent reviewer a stable candidate snapshot and the complete feature scope. After fixes, review the delta, reverify previous blocking findings and inspect affected risks. Reference prior coverage explicitly so a scoped approval cannot masquerade as complete feature coverage. Run targeted reproductions and meaningful negative controls when validating new or suspect assertions. Let CI own broad mechanical checks, while the builder proves the focused user journey using the existing affected-check primitive. Reused proof must identify its source SHA, environment, tested surface and unchanged relevant inputs; it must never be described as a fresh PASS at another head. Changes to schema, dependencies, configuration or trust boundaries can invalidate reuse. Required exact-candidate CI remains required. ([Affected checker](</Users/jono/dev/daisydebate/scripts/check-affected.ts:43>), [Workflow analysis](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/workflow.md>))

Retain security and privacy review, migration safety, bundle-secret isolation, persistence/concurrency integration, real browser journeys and negative proof that important assertions can fail. Preserve explicit owner architecture decisions rather than silently weakening gates. Remove repeated whole-suite proof after unrelated deltas, duplicate reviewers with identical scope, scripted narration and mandatory task creation for speculative improvements. Batch verified findings and update durable status at delivery boundaries. PointGuard’s updated review wording alone is insufficient: audited init-offense main and later branch scaffolds still carry conflicting twice-integration or “BRANCH FEEDBACK” contracts. Actual templates, installed consumers and verifiers need consistent treatment. ([Consumer mismatch and preserved controls](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/workflow.md>))

## Measure one working slice before adding more process

Pilot the balance on the next owner-authorized feature. Define one real journey crossing domain, persistence, API/realtime and UI, including a meaningful refusal or failure path. Build and exercise that slice early. Consume available prerequisites at a pinned dependency branch SHA rather than universally waiting for their mainline merge; record provisional integration obligations and still require the final composed candidate to pass acceptance. Decompose work where boundaries or parallelism help, not merely to produce independently green foundations. The planned-reader registry can identify orphan foundations, but it cannot substitute for a runtime consumer. ([Dependency rules and analysis](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/workflow.md>))

For that pilot, record **time to first functional persisted slice**, review publication time separately from CI/merge time, check invocations and reruns by SHA/suite, and blocked time by environment, owner decision and administration. Record fresh input, cached input and output tokens separately, with inherited baselines and imported duplicates removed. Track distinct defects found by the first broad review, additional defects found by delta reviews, and escapes after completion. Do not optimize PR count or findings count. The current corpus contains 235 native Daisy conversation files versus 11 PageSpace files with different date windows; aggregate usage cannot establish relative efficiency. Daisy Codex’s 564.9 million recorded input tokens include 548.4 million cached tokens, leaving about 16.49 million uncached. Claude cache-read exposure is also distinct from fresh input. These are recorded exposures, not billed cost or proof of degraded reasoning. ([Accounting and caveats](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/conversations.md>), [Usage snapshot](</Users/jono/dev/pointguard/research_notes/Daisy Debate workflow balance/conversation_metrics.json>))

Set an explicit completion condition: the composed journey works, actionable blocking findings are resolved and verified, final scope coverage is complete, and required exact-candidate CI passes. Stop then. Another full review needs new behavior, invalidated evidence or a specific unresolved concern; a no-progress approval wait should produce a clear blocked handoff rather than endless continuations. This is a proposed pilot, not a measured savings claim.

## Conclusion

The practical hypothesis is that **earlier composition plus independent, focused review will retain the valuable catches while shortening the expensive tail**. The evidence already identifies avoidable publication waits and execution collisions; it does not quantify total savings or prove the agents themselves reason worse. A small instrumented feature is enough to test that hypothesis before inventing another framework. If broader checks or delta reviews keep finding important new defects, keep them where that evidence supports their cost; if repeated proof adds no coverage, stop paying for it.
