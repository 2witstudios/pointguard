# Workflow rules, code evolution, and existing primitives

## Which rules create repeat work and delay the first coherent product shape?

### Takeaway
Daisy's written process mandates substantially more local verification and administration than PageSpace's repository map, but CI complexity alone cannot explain a speed ratio. The strongest concrete barriers are rerunning gates as a review prerequisite, requiring merged prerequisites before planning dependent work, and making every deferrable observation a new task in the same session.

Raw file length is only a weak token-load proxy: Daisy's graph of mandatory linked documents matters more than these counts. Daisy's start map links architecture, setup, testing, UI, five decision documents, extending, parallel work, pu workflow and epic pipeline. — [Daisy map](/Users/jono/dev/daisydebate/AGENTS.md:7), [Daisy context](/Users/jono/dev/daisydebate/.pu/agent-context.md), [PageSpace map](/Users/jono/dev/pagespace/AGENTS.md), [PageSpace Claude map](/Users/jono/dev/pagespace/CLAUDE.md).

### Inferences
- The merged-prerequisite policy may serialize design discovery and force agents to certify isolated foundational boxes before anyone exercises their combined user journey. A contract available at a stable branch SHA is technically consumable without merging; availability and final acceptance should be different dependencies.
- The repeated local builder gate + pre-push affected gate + reviewer full gates + twice-run integration + CI can duplicate unchanged proof. A new head must invalidate review coverage of the delta, but does not logically require regenerating every unchanged expensive result.
- Issue creation, evidence pages, links, board plumbing and repeated doc reads are useful individually but can become most of the critical path for small leaves. More tasks can create more edges, more records and more possible “unfinished” state without accelerating user-visible coherence.
- No evidence here proves instructions caused worse model reasoning. Plausible mechanisms are spending context/output on procedural narration, carrying contradictory sources, and optimizing for gate/record completion rather than exploring integrated behavior.

### Gaps
- Runtime, token, tool-call and quality comparison belongs to conversation and PR analysis by other researchers. No speed ratio can be established from instructions alone.
- Remote PageSpace Library contracts may differ from seeded copies. Seed contract claims must not be presented as verified live Library text.

## What does the existing review-record primitive do, and where does independence actually fail?

### Takeaway
The existing primitive already separates an exact-head independent reviewer from the builder and lets GitHub combine review with CI. Scheduling dependence is not present in the workflow DAG; the review's own prompt/verifier contract introduces the coupling, including a particularly bad incentive: zero-findings approval requires extra proof while approval with a minor or nit does not.

### Cited Findings
- Daisy `review-record.ts` validates exact head SHA, PR number, builder identity, reviewer different from builder, and APPROVE or APPROVE WITH MINORS with no open blockers/majors. The GitHub App mints status; agents do not set it. All linked records for the same head must approve, so one approving record cannot outvote a request for changes. — [Verifier](/Users/jono/dev/daisydebate/scripts/review-record.ts:118), [Workflow](/Users/jono/dev/daisydebate/.github/workflows/review-record.yml), [init-offense verifier](/Users/jono/dev/init-offense/scripts/review-record.ts:145).
- Daisy's verifier sets `clean = minors === 0 && nits === 0`, then rejects clean approval absent `bun test:integration: PASS` and `Negative control run: yes` in Gates run. Init-offense has the same logic using its configured integration command. This conditional is executable behavior, not inferred wording. — [Daisy condition](/Users/jono/dev/daisydebate/scripts/review-record.ts:139), [init-offense condition](/Users/jono/dev/init-offense/scripts/review-record.ts:166).
- The review-record workflow's verify job needs only its own App configuration gate. It has no dependency on `CI gate` or Playwright. Daisy's CI gate depends on checks/audit/migrations/integration; GitHub merge readiness requires CI gate, Playwright and review-record separately. — [Review workflow](/Users/jono/dev/daisydebate/.github/workflows/review-record.yml), [CI aggregate](/Users/jono/dev/daisydebate/.github/workflows/ci.yml:156), [Merge contract](/Users/jono/dev/daisydebate/docs/development/parallel-work.md:107).
- The record format instructs reviewer self-check and fixing the record until PASS **before** posting the verdict comment. The seeded reviewer contract repeats this. That can delay publication of useful clean review if an unrelated integration service is unavailable even though record-format and code judgment are sound. — [Self-check contract](/Users/jono/dev/init-offense/docs/development/review-record.md:68), [Reviewer deliverables](/Users/jono/dev/init-offense/drive-seed/library/reviewer-contract.html).
- Current pointguard working copy explicitly says independent review proceeds regardless of CI, focused checks verify findings, CI evidence is read rather than rerun as a prerequisite, normal verdicts remain, and verifier refusals are separately reported. It removes invented branch/main review approval stages and names init-offense's exact-head Candidate/Builder/Reviewer primitive. These are already in-progress root-session changes and were not modified by this researcher. — [Current review skill](/Users/jono/dev/pointguard/skills/review/SKILL.md:30).

### Inferences
- Clean-review proof asymmetry creates incentive to find/count a nit, or spend more time making a spotless record pass, regardless of defect risk. It should be removed; evidence obligations should depend on changed risk and acceptance coverage, not finding count.
- Keep independent exact-head review status and required CI checks, but remove CI rerun text-matching from the code-review verdict verifier. A review should be able to approve reviewed code while merge remains blocked by missing required CI/proof. No new verdict or “branch feedback” tier is necessary.
- A delta record should identify prior coverage and changed head/diff, reverify every prior blocking fix and inspect new behavior. Final merge readiness must have complete composed coverage; reuse is explicit and attributable, never a fabricated fresh PASS.

### Gaps
- Actual GitHub live ruleset configuration was not queried in this scoped audit. Written and committed intended requirements are verified; current enforcement may differ.
- The all-records-must-approve rule can retain malformed records as a veto until corrected. No incident involving same-SHA contradictory records was measured here.

## What history and balanced policy preserve quality without recreating the bureaucracy?

### Takeaway
Daisy has already removed a large locally invented autonomy framework; using the remaining primitives is the consistent direction. Preserve meaningful security and state-integrity checks, reduce repeated proof and administration, and make the first deliverable a coherent exercised vertical slice.

### Inferences
- Proposed balanced policy: plan one coherent user journey first, including domain→persistence→route/realtime→UI and a meaningful failure path. Decide major security/architecture intent early, but let foundational and consumer work compose at stable branch SHAs rather than waiting for independent main merges. Keep human activation/sign-off leaves where already justified.
- Use the existing affected graph for the builder inner loop and first PR. Required CI owns full mechanical checks. Reviewer reads stable snapshot and prior proof, runs targeted reproductions, adds negative controls for high-risk/new test mechanisms or suspect assertions, and immediately publishes findings independently of CI.
- Reuse unchanged expensive service proof by recording source SHA, environment and tested surface plus why relevant inputs did not change. CI at the exact candidate remains authoritative for mandatory merge checks. Rerun broad local proof when lockfile/config/schema/trust boundaries or actual unresolved concerns invalidate reuse, not simply because a comment or doc changed.
- Batch administration once per handoff/review boundary. One authoritative review record per candidate, concise evidence table, PR link and task status suffice; avoid repeated narrative prompts, copied full contracts and synthetic branch/main verdicts. File verified actionable defects in batches; do not turn speculative improvement brainstorming into mandatory leaf creation.
- Retain trust-boundary review, negative controls that prove important assertions can fail, durable/atomicity integration, privacy/logging checks, auth/authorization review, migrations, bundle leakage and real browser composition. Cut repeated proof of unchanged behavior, output choreography and ornamental completeness rather than the catches.
- Measure before further policy tightening: time to first exercised coherent slice, elapsed blocked on review vs CI vs environment vs board work, total input/output tokens, duplicate proof count, confirmed high-severity defects, regression escapes and rework. Never optimize purely for PR count or test count; tiny “green boxes” can conceal an incomplete whole.
